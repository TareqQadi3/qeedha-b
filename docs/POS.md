# نقطة البيع (POS) — تصميم (يُبنى في المرحلة 3)

هذا الملف تصميم مرجعي، لا يوجد كود POS في المرحلة الأولى.

## المتطلبات الوظيفية (من وثيقة المواصفات)
مسح باركود، بحث، تعديل كمية، خصومات حسب الصلاحيات، تعليق/استكمال فاتورة،
مرتجعات، طرق دفع متعددة (split payment)، طباعة فاتورة، فاتورة إلكترونية،
قيّدها كطريقة دفع عند الربط فقط.

## تدفق البيع
```text
بناء السلة → حساب الخصم/الضريبة → الدفع (نقدي/بطاقة/تحويل/[تكامل نشط]) →
إصدار الفاتورة (ZATCA) → طباعة/QR → إتمام
```

## نقاط تصميم حرجة
- **الخصم/تجاوز السعر**: يتطلب صلاحية `sales.discount.override` فوق حد معيّن،
  ويُسجَّل في `audit_logs` بالسبب.
- **الإبطال (Void)**: يتطلب موافقة مدير + Audit log، ولا يُحذف السجل أبدًا.
- **المرتجعات**: مرتبطة ببند الفاتورة الأصلي (line item)، وليست مرتجعًا عامًا
  بمبلغ حر.
- **السلات المعلّقة (Held carts)**: تخزين مؤقت (hard delete مقبول)، لا أثر
  محاسبي حتى الدفع الفعلي.
- **الوردية (Cash session)**: فتح برصيد ابتدائي، كل حركة نقدية مرتبطة بالوردية
  المفتوحة، إغلاق بمطابقة الفعلي مقابل المتوقع وتسجيل الفرق.
- **الدفع عبر تكامل خارجي (قيّدها لاحقًا)**: POS لا يعرف تفاصيل المزوّد، فقط
  يستدعي `IntegrationConnection` النشطة من نوع `payment` ويتعامل مع حالات
  `pending/success/failed/cancelled/refunded` بشكل عام. راجع
  `QEEDHA_INTEGRATION.md`.

## Offline-first (يُصمَّم بالتفصيل عند بدء المرحلة 3)
- Local queue للفواتير + Idempotency Key لكل فاتورة تُنشأ محليًا.
- مزامنة عند عودة الاتصال، مع حل تعارض المخزون (مثلًا: بيع نفس آخر قطعة من
  جهازين offline في نفس الوقت) — القرار التفصيلي (استراتيجية Conflict
  Resolution) يُتخذ عند هذه المرحلة وليس الآن.
- العمليات التي تتطلب اتصالًا إجباريًا: الفوترة الإلكترونية ZATCA Phase 2
  Clearance (فواتير B2B)، أي دفع عبر تكامل خارجي.
