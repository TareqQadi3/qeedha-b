# استراتيجية الاختبار (Testing)

## المبدأ
كل مرحلة تُختبر قبل الانتقال للتالية (طلب صريح من المستخدم) — لا نبني ميزة
جديدة فوق أساس غير مختبر.

## أنواع الاختبار

| النوع | الأداة | متى |
|---|---|---|
| Unit | Jest | لكل Service منطق أعمال (حسابات، قواعد صلاحية، RBAC) |
| Integration/e2e | Jest + Supertest + قاعدة بيانات اختبار حقيقية | لكل Module جديد (auth, iam, integrations) |
| DB constraints | اختبار مباشر عبر Prisma على قاعدة اختبار | RLS policies، Unique constraints |

## اختبارات المرحلة 1 (الحد الأدنى الإلزامي)
- تسجيل منشأة جديدة ينشئ Company + Branch افتراضي + Warehouse افتراضي +
  User + Membership واحدة بدور Owner بكل الصلاحيات.
- تسجيل الدخول الناجح/الفاشل (كلمة مرور خاطئة، مستخدم غير موجود، حساب معطّل).
- Refresh token: تجديد ناجح، رفض توكن منتهٍ/مُبطَل، إبطال السلسلة عند إعادة
  استخدام توكن مُستهلَك، واستمرار العمل بعد اختيار/تبديل المنشأة.
- RBAC: مستخدم بدون صلاحية `X` يُرفض بـ403 عند محاولة الوصول لمسار يتطلبها.
- **عزل المستأجرين**: مستخدم من منشأة A لا يستطيع قراءة/تعديل أي سجل من منشأة
  B، حتى بمعرفة الـID مباشرة (اختبار صريح لهذه الحالة تحديدًا، بما فيه فحص
  RLS مباشر على `memberships`).
- Audit log: عملية حساسة (مثل تغيير دور مستخدم) تُنتج سجل Audit صحيح.
- Integration skeleton: إنشاء/قراءة `integration_connections` بحالاته دون أي
  استدعاء فعلي لخدمة خارجية (لأنه لا يوجد Adapter بعد).

## اختبارات نموذج الهوية متعدد المنشآت (Membership) — إلزامية بعد Auth/IAM refactor
راجع `docs/DOMAIN_MODEL.md` للنموذج الكامل. الحد الأدنى المُختبَر فعليًا في
`backend/test/app.e2e-spec.ts`:
1. مستخدم بعضوية واحدة فقط: تسجيل الدخول يمنح tokens مباشرة، بدون شاشة اختيار.
2. مستخدم بعضويتين (نفس البريد مُرفَق بمنشأتين عبر `IamService.createUser`):
   تسجيل الدخول يُعيد `tenantSelectionRequired` بدل tokens.
3. اختيار منشأة يملك المستخدم عضوية نشطة فيها عبر `/auth/select-tenant` ينجح.
4. اختيار منشأة لا يملك المستخدم أي عضوية فيها (Tenant C) عبر
   `/auth/select-tenant` أو `/auth/switch-tenant` يُرفض بـ403 — يثبت أن
   الخادم لا يثق بـ`companyId` القادم من العميل، بل يتحقق من Membership
   فعليًا في كل مرة.
5. نفس الشخص بدور مختلف تمامًا في كل منشأة (مثلًا Owner في A، Accountant في
   B) — يُتحقق من أن `roles`/`permissions` في `/auth/me` تختلف فعليًا بين
   الجلستين.
6. عضوية `suspended` تفقد كل وصول فورًا (حتى لمسارات بلا `@RequirePermissions`)
   عبر `MembershipGuard`، رغم أن الـaccess token ما زال صالحًا فنيًا.
7. إرفاق مستخدم موجود بمنشأة يملك فيها عضوية بالفعل → `409 Conflict`.
8. إرفاق مستخدم موجود لا يُغيّر كلمة مروره أبدًا، حتى لو أُرسلت كلمة مرور في
   الطلب — يُتحقق بتسجيل الدخول لاحقًا بكلمة المرور الأصلية.
9. RBAC/tenant-isolation tests السابقة (البند أعلاه) تستمر بالنجاح كاملة بعد
   إعادة الهيكلة — لا تراجع.

## اختبارات المرحلة 2 (Products/Inventory/Customers/Suppliers) — إلزامية
راجع `backend/test/phase2.e2e-spec.ts` (33 اختبارًا إجماليًا مع اختبارات
المرحلة 1). الحد الأدنى المُختبَر فعليًا:

**المنتجات**: دورة CRUD + Audit كاملة (بما فيها أحداث `price_change`/
`sku_change` المنفصلة)، بحث بالاسم/SKU/الباركود، `SKU` وباركود فريدان لكل
منشأة وليس عالميًا (نفس القيمة تُقبَل لمنشأة أخرى)، رفض ربط منتج
بتصنيف/علامة/وحدة تابعة لمنشأة أخرى، رفض قراءة/تعديل/حذف منتج من منشأة أخرى
حتى بمعرفة الـID، رفض الوصول بلا صلاحية.

**المخزون**: رصيد افتتاحي + تسوية + رفض تسوية تُنتج رصيدًا سالبًا، تحويل
فعلي بين مستودعين، **اختبار تزامن بـ10 طلبات HTTP متزامنة حقيقية** على نفس
`(warehouse, product)` يتحقق أن الرصيد النهائي = 10 بالضبط وعدد حركات
`stock_movements` الناتجة = 10 بالضبط، دورة جرد كاملة (إنشاء → تحديث سطور →
اعتماد → التحقق من تحديث الأرصدة تلقائيًا → التحقق من تجميد السطور بعد
الاعتماد)، رفض العمل على مستودع تابع لمنشأة أخرى، رفض الوصول بلا صلاحية.

**العملاء والموردون**: دورة كاملة، الجوال غير فريد عالميًا (يُقبَل تكراره)،
رفض قراءة/تعديل عميل أو مورد من منشأة أخرى، `reference` فريد لكل منشأة إن
وُجد، رفض الوصول بلا صلاحية.

**RLS مباشر**: استعلام Prisma مباشر (بدون طبقة الخدمة) على `products`/
`customers` يتحقق أن RLS وحدها (بلا أي فحص تطبيقي) تمنع القراءة عبر المنشآت.

## اختبارات المرحلة 2.1 (نطاق الفروع/المستودعات) — إلزامية
راجع `backend/test/phase2.e2e-spec.ts` قسم "نطاق الفروع/المستودعات" (33
اختبار المرحلة 2 + 5 اختبارات جديدة = 38 إجمالًا). يغطي مصفوفة الاختبار
المطلوبة كاملة:

- **نفس المنشأة / فرع مُصرَّح** → PASS: عضو بإسناد دور مقيّد بفرع الوحدة
  الافتراضي ينجح في رصيد افتتاحي على مستودع ذلك الفرع.
- **نفس المنشأة / فرع غير مُصرَّح** → FAIL (403): نفس العضو يُرفض عند تسوية،
  تحويل (أي من الطرفين)، أو إنشاء جرد على مستودع تابع لفرع آخر بنفس المنشأة.
- **نطاق الفرع يشمل كل مستودعاته**: عضو مُصرَّح لفرع كامل (لا لمستودع واحد)
  ينجح على أكثر من مستودع تابعين لذلك الفرع.
- **إسنادا دور (فرعان)**: عضو بإسنادَي `MembershipRole` بفرعين مختلفين ينجح
  على مستودعات كلا الفرعين معًا (اتحاد النطاقات).
- **نطاق كامل تلقائي لفرع جديد**: عضو Owner (`branchId: null` عند التسجيل)
  ينجح فورًا على فرع/مستودع أُنشئا بعد إسناد دوره، بلا أي إسناد إضافي.
- **عضوية معلَّقة** → FAIL (403 عبر `MembershipGuard`، حتى لمستودع ضمن نطاقها).
- **مختلف المنشأة / مستودع** → FAIL (404 — سلامة مرجعية عبر المنشآت، غير
  متأثرة بمنطق النطاق الجديد).
- **صلاحية سارية + نطاق فرع غير سارٍ** → FAIL (403 — الصلاحية وحدها لا تكفي).
- **قوائم القراءة لا ترفض، تُصفّي**: طلب `warehouseId` خارج النطاق على
  `GET /inventory/stock-levels` يُرجع 200 بنتيجة فارغة، لا 403.
- **سيناريو متعدد المستأجرين الكامل**: منشأتان (A بفرعين A1/A2، B بفرع B1)،
  أربعة مستخدمين بنطاقات مختلفة (A1 فقط، A1+A2 معًا، B1 عبر Owner B)، يتحقق
  أن كل تركيبة وصول/رفض تطابق النموذج المطلوب بالضبط.
- **بلا تراجع**: كل اختبارات المرحلة 2 الـ33 (بما فيها اختبار التزامن
  بـ10 طلبات) تستمر بالنجاح كاملة بعد هذا التغيير.

## اختبارات المرحلة 3 (POS/Sales/Payments/Invoices) — إلزامية
راجع `backend/test/phase3.e2e-spec.ts` (25 اختبارًا جديدًا؛ 38 اختبار سابق +
25 = 63 إجمالًا). يغطي مصفوفة الاختبار المطلوبة كاملة:

**التفويض**: بلا توكن → 401. عملية بيع من منشأة أخرى غير مرئية حتى بمعرفة
الـID → 404. مستودع من منشأة أخرى تمامًا → 404. عضو مقيّد بفرع يُرفض بيع من
مستودع فرع آخر بنفس المنشأة → 403. جهاز POS تابع لفرع مختلف عن المستودع →
409. جهاز POS غير نشط → 409؛ جهاز من منشأة أخرى → 404. عضوية معلَّقة تُرفض
حتى مع صلاحية `sales.create` سارية → 403. كاشير بلا `sales.cancel` → 403 عند
محاولة الإلغاء.

**الوظيفي**: بيع سطر واحد يحسب الإجمالي/الضريبة بدقة، يخصم المخزون، يولّد
فاتورة، ويُسجَّل Audit. بيع بعدة سطور مع خصم على سطر يحسب الإجماليات الجزئية
والكلية بشكل صحيح. Split payment (نقدي + بطاقة) يُقبَل حين يتطابق المجموع مع
الإجمالي بالضبط، ويُرفض بـ400 حين لا يتطابق (حالة "فشل دفع"). خصم أكبر من
قيمة السطر → 400. مخزون غير كافٍ → 409 بلا إنشاء أي سجل بيع. منتج معطّل لا
يمكن بيعه. بيع بعميل وبيع بلا عميل (نقدي سريع) كلاهما يعمل. إلغاء بيع مكتمل
يُرجع المخزون ويُعلّم الفاتورة كملغاة؛ إلغاء مرتين → 409. حالة الدفع `pending`
مدعومة في نموذج البيانات (تحقُّق مباشر عبر Prisma، بلا تدفق HTTP وهمي —
لا مزوّد خارجي فعلي بعد).

**التزامن وIdempotency**: طلب مكرر بنفس `clientReferenceId` (تسلسليًا، ثم 5
طلبات متزامنة حقيقية) يُنتج سجل بيع واحد فقط دائمًا. **عمليتا بيع متزامنتان
حقيقيتان** تحاولان بيع كمية تتجاوز المتاح مجتمعتين (Stock=10، كل طلب يبيع 7)
— واحدة فقط تنجح (201)، الأخرى تُرفض (409)، الرصيد النهائي = 3 بالضبط، ولا
يوجد أي احتمال لرصيد سالب. 10 طلبات بيع متزامنة حقيقية تُنتج 10 أرقام فاتورة
فريدة بلا أي تكرار.

**القوائم والصلاحيات**: عضو بلا `sales.create` → 403. قائمة المبيعات/الفواتير
تعرض ما يخص المنشأة فقط، مع صفحات.

**RLS مباشر**: استعلام Prisma مباشر (بدون طبقة الخدمة) على `sales`/`invoices`
يتحقق أن RLS وحدها تمنع القراءة عبر المنشآت.

**Browser test (Playwright)**: تدفق كامل حقيقي عبر متصفح فعلي (تسجيل دخول →
فتح POS → بحث عن منتج → إضافة للسلة → تعديل كمية → اختيار عميل → دفع نقدي →
إتمام البيع → التحقق من ظهور رقم الفاتورة في الواجهة ومطابقته عبر الـAPI →
التحقق من تحديث المخزون عبر الـAPI) + سيناريو فشل واحد (مخزون غير كافٍ يعرض
رسالة خطأ واضحة في الواجهة ولا يُغيّر الرصيد). نُفِّذ يدويًا بتشغيل فعلي
متزامن للـbackend/frontend، بلا أخطاء console حقيقية (السجل الوحيد الملاحظ
هو تسجيل طلب الشبكة 409 المتوقَّع لسيناريو الفشل نفسه).

**بلا تراجع**: كل اختبارات المراحل 1/2/2.1 الـ38 تستمر بالنجاح كاملة.

## اختبارات المرحلة 4 (Purchases/Expenses/Accounting Foundation) — إلزامية
راجع `backend/test/phase4.e2e-spec.ts` (28 اختبارًا جديدًا؛ 63 اختبار سابق
+ 28 = **91 إجمالًا**). يغطي مصفوفة الاختبار المطلوبة كاملة عبر 6 مجموعات:

**دليل الحسابات (Chart of Accounts)**: تسجيل منشأة جديدة ينشئ دليل حسابات
افتراضيًا كاملًا (كل الحسابات الموثَّقة في `docs/CHART_OF_ACCOUNTS.md`).
إنشاء حساب جديد يتطلب `accounting.manage`، وتعديله (`name`/`isActive`)
يعمل. رمز حساب مكرر لنفس المنشأة → `409`. **لا Endpoint لإنشاء أو تعديل
قيد محاسبي يدويًا** (منع الإدخال المزدوج — تحقُّق مباشر أن السطح غير
موجود، لا مجرد صلاحية مرفوضة). حساب من منشأة أخرى → `404` عند التعديل.

**سلامة القيد المحاسبي (Double-Entry Integrity)**: قيد متوازن (استدعاء
`JournalService` مباشرة) ينجح. قيد غير متوازن (مدين ≠ دائن) → يُرفض. قيد
بقيمة صفرية → يُرفض. عكس قيد مُعكوس بالفعل → يُرفض (409).

**المشتريات (Purchases)**: إنشاء أمر شراء ثم استلامه يزيد المخزون ويولّد
قيدًا متوازنًا (مخزون + ضريبة مدخلات = ذمم دائنة). مستودع/مورد من منشأة
أخرى → `404`. استلام مرتين → `409` (لا يُستلَم المخزون مرتين). **استلام
متزامن حقيقي** لنفس أمر الشراء: مرة واحدة فقط تنجح، المخزون لا يتضاعف. 10
أوامر شراء من طلبات متزامنة حقيقية → 10 أرقام مرجعية فريدة بلا تكرار.
طلب مكرر بنفس `clientReferenceId` → نفس أمر الشراء دون تكرار. إلغاء أمر
لم يُستلَم يعمل؛ إلغاء أمر مُستلَم → `409`. عضو مقيّد بفرع لا يمكنه الشراء
لمستودع فرع آخر بنفس المنشأة → `403`. عضو بلا `purchases.create` → `403`.

**المصروفات (Expenses)**: إنشاء مصروف ينشئ قيدًا متوازنًا (مصروف =
نقدية)، ويُسجَّل Audit. تعديل مبلغ مصروف يعكس القيد القديم وينشئ قيدًا
جديدًا صحيحًا. حذف مصروف يعكس القيد؛ حذف/تعديل مصروف محذوف بالفعل → `409`
في كلتا الحالتين. مصروف مرتبط بفرع خارج نطاق العضوية → `403`. عضو بلا
`expenses.create` → `403`. مصروف من منشأة أخرى غير مرئي حتى بمعرفة الـID
→ `404`. 5 طلبات متزامنة حقيقية بنفس `clientReferenceId` → مصروف واحد فقط.

**التكامل مع المحاسبة (Sale/Purchase/Expense → Accounting)**: بيع مكتمل
ينتج قيدًا متوازنًا؛ إلغاؤه ينتج قيدًا عكسيًا ويُعلّم الأصلي `reversed`.

**RLS مباشرة على جداول المرحلة الرابعة**: استعلام Prisma مباشر (بدون طبقة
الخدمة) على `purchases`/`expenses`/`accounts`/`journal_entries` يتحقق أن
RLS وحدها (بلا أي فحص تطبيقي) تمنع القراءة عبر المنشآت.

**Browser test (Playwright)**: تدفق يدوي حقيقي عبر متصفح فعلي (تسجيل دخول
→ المشتريات: إنشاء أمر شراء ثم استلامه، التحقق من زيادة المخزون عبر الـAPI
→ المصروفات: تسجيل مصروف، التحقق من توازن قيده عبر الـAPI → المحاسبة:
دليل الحسابات ظاهر في تبويب "دليل الحسابات"، نافذة تفاصيل قيد محاسبي تُظهر
مدين = دائن في تبويب "القيود المحاسبية"). سكربت مؤقت غير مُدرَج في
المستودع (نفس اتفاقية Playwright اليدوية من المرحلة 3) — نجحت كل الخطوات
بلا أخطاء console حقيقية.

**بلا تراجع**: كل اختبارات المراحل 1/2/2.1/3 الـ63 تستمر بالنجاح كاملة.

## اختبارات Milestone 1: Accounting Completion — إلزامية
راجع `backend/test/milestone1.e2e-spec.ts` (21 اختبارًا جديدًا؛ 91
اختبار سابق + 21 = **112 إجمالًا**، مُتحقَّق فعليًا بتشغيل
`npx jest --config ./test/jest-e2e.json --runInBand` — راجع "بلا تراجع"
أدناه لكيفية إعادة التحقق). يغطي مصفوفة الاختبار كاملة عبر 6 مجموعات:

**التقارير المالية (Trial Balance / General Ledger / P&L / Balance
Sheet)**: ميزان مراجعة متوازن (مدين = دائن) بعد بيع ومصروف، ورصيد صافٍ
صحيح لحساب النقدية. نطاق التاريخ (`dateFrom`/`dateTo`) يُقصي القيود
خارج المدى. دفتر أستاذ حساب معيّن برصيد جارٍ صحيح. صافي الربح = الإيرادات
− المصروفات، ويظهر كبند "أرباح مرحّلة غير مقفلة" (`computed: true`)
متوازن في الميزانية العمومية. حساب من منشأة أخرى في دفتر الأستاذ → `404`
(IDOR). عضو بلا `accounting.reports.view` → `403` على كل التقارير
الأربعة.

**الذمم المدينة/الدائنة (AR/AP Subledger)**: AR يعود فارغًا هيكليًا حتى
بعد بيع مرتبط بعميل — يثبت القيد الموثَّق (لا بيع آجل في النظام)، وليس
خطأ. AP يعرض رصيدًا صحيحًا لكل مورد بعد استلام مشتريات + كشف حساب
مفصَّل. كشف حساب مورد من منشأة أخرى → `404` (IDOR). عضو بلا
`accounting.ar.view`/`ap.view` → `403`.

**الأرصدة الافتتاحية (Opening Balances)**: تسجيل رصيد متوازن ينجح، ولا
يمكن تسجيل آخر قبل عكسه (`409`). رصيد غير متوازن → `422`. عكس الرصيد
يسمح بتسجيل رصيد جديد؛ عكسه بلا رصيد نشط → `404`. **طلبان متزامنان
حقيقيان** لتسجيل رصيد افتتاحي — واحد فقط ينجح (`201`)، الآخر `409`
(الفهرس الفريد الجزئي على مستوى Postgres، لا فحص تطبيقي فقط)، والتحقق
المباشر عبر Prisma أن صفًا واحدًا فقط `posted` موجود فعليًا. عضو بلا
`accounting.opening_balance.manage` → `403`.

**الفترات المحاسبية (Fiscal Periods)**: إنشاء فترة، وفترة متقاطعة معها
→ `409`، وتاريخ بداية بعد النهاية → `400`. إقفال الفترة الحالية يمنع
ترحيل قيود جديدة (مصروف جديد → `409`)؛ إعادة الفتح تسمح مجددًا. إقفال
فترة مُقفلة بالفعل → `409`؛ إعادة فتح فترة مفتوحة بالفعل → `409`. فترة
محاسبية من منشأة أخرى → `404` عند محاولة إقفالها (IDOR). عضو بلا
`accounting.period.manage` → `403`.

**نطاق الفروع في التقارير (Branch scope)**: محاسب مقيّد بفرع واحد لا
يرى في دفتر الأستاذ إلا حركات فرعه (سطر واحد)، بينما Owner غير المقيَّد
يرى حركات كل الفروع (سطرين) على نفس الحساب — نفس بيانات الاختبار
بالضبط، فرق واحد فقط هو نطاق العضوية المستعلِمة.

**بلا تراجع**: كل اختبارات المراحل 1/2/2.1/3/4 الـ91 تستمر بالنجاح
كاملة، مع تصحيح واحد داخل `journal.service.ts` (ترتيب تعليم القيد
الأصلي `reversed` قبل إنشاء قيد العكس، راجع `docs/ACCOUNTING.md` "حارس
التزامن") — لم يُغيّر أي سلوك أو استجابة API ملحوظة لأي اختبار سابق.

**Browser test (Playwright)**: تدفق يدوي حقيقي عبر متصفح فعلي (تسجيل
منشأة → زرع بيع/مصروف/شراء عبر الـAPI → صفحة التقارير: زيارة التبويبات
الأربعة والتحقق من عرض بيانات حقيقية → صفحة الذمم: تبويبا AR/AP → تبويب
الأرصدة الافتتاحية في `/accounting`: إنشاء + عرض → تبويب الفترات
المحاسبية: إنشاء + عرض) — كل الخطوات نجحت بلا أخطاء console. عِلّة
تنسيق فعلية اكتُشفت وصُحِّحت أثناء هذا الاختبار: الأرقام المالية كانت
تُعرَض بـ`toLocaleString('ar-SA', ...)` (أرقام هندية شرقية، مثل ٢٠٫٠٠)
بدل الأرقام الغربية المستخدمة في كل صفحة أخرى بالتطبيق — صُحِّحت إلى
`.toFixed(2)` في `ReportsPage.tsx` و`ReceivablesPayablesPage.tsx`.

## Playwright — الآن مجموعة مُلتزَمة (committed) وليست سكربتات مؤقتة

**تصحيح إطار سابق**: أقسام "Browser test (Playwright)" أعلاه (المرحلة
3/4/Milestone 1) وصفت تشغيلًا **يدويًا** لسكربتات مؤقتة (scratchpad) لم
تُحفظ في المستودع. هذا الوصف كان دقيقًا وقتها. **في Milestone 2 هذا لم
يعد الحال**: توجد الآن مجموعة Playwright **مُلتزَمة فعليًا في المستودع**
وقابلة للتكرار من أي شخص، لا سكربتات مؤقتة تُكتب وتُشغَّل يدويًا في كل
مرة.

`frontend/playwright.config.ts`: يفترض أن الـbackend API يعمل ومتاح
مسبقًا (نفس افتراض مجموعة e2e الخلفية — Postgres مُهاجَر ومزروع)، ويبدأ
خادم تطوير الواجهة الأمامية فقط بنفسه عبر `webServer` (`npm run dev`).

**الملفات**:
- `frontend/e2e/helpers.ts`: مساعدات مشتركة (تسجيل منشأة، دخول، خروج،
  توليد معرّف فريد).
- `frontend/e2e/golden-path.spec.ts`: الرحلة الكاملة عبر الواجهة الحقيقية
  ضد الـbackend الحقيقي (لا طلبات مُقلَّدة) — تسجيل → منتج → مخزون (رصيد
  افتتاحي) → عميل → مورد → شراء → استلام → بيع POS → دفعة → فاتورة →
  مصروف → محاسبة (القيود تُظهر البيع/الشراء/المصروف) → تقارير (ميزان
  المراجعة متوازن) → الذمم (AP يُظهر المورد) → تسجيل خروج → دخول مجددًا.
- `frontend/e2e/tenant-isolation.spec.ts`: تسجيل منشأتين منفصلتين
  والتحقق أن منتجًا أنشأته المنشأة الأولى غير مرئي للثانية عبر الواجهة
  الحقيقية.

**نُفِّذت المجموعتان فعليًا ضد الحزمة الحقيقية الكاملة (backend + Postgres
مُهاجَر ومزروع + frontend) خلال هذه الجلسة ونجحتا (2/2)** — ليس وصف نيّة،
تشغيل متصفح آلي حقيقي وموثَّق.

تشغيل محلي: `cd frontend && npm run test:e2e` (يتطلب backend يعمل ومهاجَر
ومزروع مسبقًا، تمامًا مثل `backend`'s `npm run test:e2e`).

## CI (GitHub Actions) — Milestone 2

`.github/workflows/ci.yml` (جديد): ثلاث jobs مستقلة —
1. **`backend`**: حاوية خدمة Postgres، `npm ci`، `prisma generate`،
   `lint`، `tsc --noEmit`، `build`، `prisma migrate deploy`، إنشاء دور
   `qeedha_auth_lookup` عبر سكربتات `manual-sql` الموجودة أصلًا، بذر
   الصلاحيات/الأدوار، ثم مجموعة e2e الخلفية كاملة.
2. **`frontend`**: `npm ci`، `lint`، `build`، `npm run test` (Vitest).
3. **`e2e`**: Postgres خدمة منفصلة، يبني ويشغّل الـbackend الحقيقي، يثبّت
   متصفحات Playwright (`npx playwright install --with-deps chromium`)،
   يشغّل مجموعة Playwright المُلتزَمة ضده، ويرفع تقرير HTML كـartifact
   عند الفشل.

**تنبيه صريح مهم**: مِلفّ الـYAML تحقَّق من صحته النحوية فقط
(`python3 -c "import yaml; yaml.safe_load(...)"` نجح) — **لم يُشغَّل فعليًا
على أي GitHub Actions runner حقيقي على الإطلاق**، لأن بيئة التطوير هذه لا
تملك وصولًا لتشغيله. لا يُدَّعى أنه "ينجح على CI" — هو جاهز وصحيح
نحويًا، والتنفيذ الفعلي غير مُتحقَّق منه. راجع `docs/DEPLOYMENT.md`
"القيود المعروفة".
