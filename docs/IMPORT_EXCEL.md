# استيراد من Excel (Import Wizard) — Milestone 3، منفَّذ

نظام استيراد بيانات حقيقي من ملفات Excel (.xlsx) داخل qeedha B كـSaaS
متعدد المستأجرين، مبني فوق خدمات الكتالوج/المخزون/الأطراف الموجودة أصلًا
(`ProductsService`، `CatalogService`، `CustomersService`،
`SuppliersService`، `InventoryService.setOpeningBalance`) — لا منطق أعمال
موازٍ جديد. الوحدة: `backend/src/modules/imports`.

**الفرق عن التصميم الأولي أدناه** (القسم الذي كان موجودًا قبل هذا
الـMilestone، محفوظ في الأسفل كمرجع تاريخي لما كان مخطَّطًا): لا تحديث
صامت/صريح لسجل موجود بمطابقة SKU — **SKU/باركود/مرجع مكرر مع بيانات
موجودة يُرفَض كخطأ في ذلك الصف**، ولا يُنشئ ولا يُحدِّث شيئًا. قرار تبسيط
متعمَّد: تحديث سجل قائم عبر استيراد جماعي يحمل مخاطر Overwrite أعلى
بكثير من إنشاء سجل جديد، ويحتاج تصميم Preview/Confirm مختلف (عرض
"قبل/بعد" لكل حقل سيتغيّر) لم يكن ضروريًا لهذه المرحلة. يبقى نقطة توسّع
واضحة لاحقًا إن احتاجها تجّار حقيقيون.

## 1) File Storage

`backend/src/modules/storage` — abstraction واضحة (`FileStorageProvider`
interface) لا يرتبط النظام بمزوّد تخزين واحد:

- **`LocalFileStorageProvider`** (المُنفَّذ الوحيد فعليًا حتى الآن، ومُتحقَّق
  منه بالتشغيل): يكتب على القرص المحلي تحت `STORAGE_LOCAL_DIR` (افتراضي
  `./storage-data`، خارج git وخارج أي مسار يُخدَّم كملفات ثابتة).
- **مزوّد S3-compatible لاحقًا**: الواجهة مصمَّمة لهذا (`save`/`read`/`delete`
  بمفتاح مجرَّد)، لكنه **لم يُنفَّذ في هذه المرحلة** — لا اعتمادات/حساب S3
  متاح لبنائه واختباره فعليًا، وتنفيذه دون تحقق حقيقي يخالف مبدأ "لا تدّعِ
  نجاح شيء لم يُختبَر". `StorageModule` يختار المزوّد عبر `STORAGE_DRIVER`
  (افتراضي `local`)؛ أي قيمة أخرى تفشل بدء التشغيل صراحة بدل السقوط الصامت
  لمزوّد افتراضي.

**مفاتيح التخزين مُولَّدة من الخادم دائمًا**: `imports/<companyId>/<jobId>/source.xlsx`
— لا يُشتَق أي جزء من المسار من اسم الملف الذي رفعه المستخدم
(`StorageService.buildImportFileKey`)، فلا يمكن لاسم ملف خبيث
(`../../etc/passwd`، فواصل مسار، بايتات تحكم) أن يؤثر على مكان الكتابة
إطلاقًا. اسم الملف الأصلي يُحفَظ منفصلًا (`ImportJob.originalFilename`)
للعرض فقط بعد تنظيفه (`StorageService.sanitizeDisplayFilename`)، وليس
للاستخدام كمسار أبدًا. `LocalFileStorageProvider.resolvePath` يتحقق أيضًا
(دفاع إضافي، وليس مسارًا يُفترض الوصول إليه فعليًا) أن أي مفتاح لا يخرج
عن `STORAGE_LOCAL_DIR`.

**عزل حسب المنشأة**: كل مفتاح يبدأ بـ`companyId` الخاص بالمنشأة صاحبة
الملف. لا يوجد أي Endpoint لتنزيل ملف استيراد خام مباشرة (غير مطلوب في
هذه المرحلة) — القراءة الوحيدة للملف المخزَّن تحدث داخليًا في
`ImportsService` (Preview/Validate/Confirm)، وتمر دائمًا عبر
`getOwned()` الذي يتحقق من ملكية `companyId` قبل أي وصول، بالإضافة لـRLS
على `import_jobs` نفسه.

## 2) Import Job — نموذج البيانات والحالات

جدول `import_jobs` (`docs/DATABASE.md` القسم 8) — `companyId`،
`actorMembershipId`/`actorUserId`، `entityType`، `status`، `fileKey`،
`originalFilename`، `fileSizeBytes`، `detectedColumns`/`columnMapping`
(JSONB)، `totalRows`/`validRows`/`errorRows`/`importedRows`،
`validationErrors` (JSONB، محدود بـ`MAX_STORED_VALIDATION_ERRORS=500`)،
`clientReferenceId` (idempotency، نفس نمط Sale/Purchase/Expense)،
timestamps. **لا جدول `import_job_rows` منفصل** (كان مخطَّطًا في التصميم
الأولي) — نتيجة كل صف تُعاد حسابها من الملف المخزَّن عند كل خطوة، والنتيجة
النهائية المحدودة العدد تُخزَّن كـJSON على المهمة نفسها، لا صف قاعدة بيانات
مستقل لكل سطر Excel (قد يصل 5000 صف).

**الحالات** (`ImportJobStatus`): `uploaded → analyzing → ready →
validating → validated → importing → completed`، مع `failed`/`cancelled`
كحالتين نهائيتين بديلتين. `ready`/`validated` قابلتان للعودة لبعضهما عبر
إعادة الربط (Mapping تعديل بعد Validate يُعيد الحالة لـ`ready`).

## 3) أنواع البيانات المدعومة

`products`، `barcodes` (إضافة باركود لمنتج موجود عبر SKU)، `categories`،
`units`، `customers`، `suppliers`، `opening_stock`. القائمة الكاملة
للحقول المطلوبة/الاختيارية لكل نوع: `backend/src/modules/imports/constants/import-field-defs.ts`
(مصدر حقيقة واحد يُستخدم في الـBackend وتعرضه الواجهة الأمامية عبر
`GET /imports/entity-types`).

`opening_stock` يختلف عن البقية: المستودع المستهدف (`targetWarehouseId`)
يُحدَّد **مرة واحدة عند إنشاء المهمة** (وليس كعمود في الملف) لأنه يجب أن
يمر بنفس فحص نطاق الفروع (`branchScope`) الذي يمر به أي كتابة مخزون أخرى.

## 4) التدفق: Upload → Detect → Map → Preview → Validate → Confirm → Import → Audit

1. **Upload** (`POST /imports/jobs`، multipart): يتحقق من نوع الملف
   (بصمة ZIP الحقيقية لـxlsx، لا الاعتماد على Content-Type وحده) وحجمه
   (`MAX_IMPORT_FILE_SIZE_BYTES` = 5MB)، يخزّن الملف، ثم يحلّله فورًا
   (متزامن — الملف صغير بما يكفي، لا حاجة لـQueue في هذه المرحلة).
2. **Detect**: صف العناوين + اقتراح ربط تلقائي (`suggestMapping` — مطابقة
   نصية مُطبَّعة لأسماء أعمدة معروفة، عربي/إنجليزي) — **اقتراح فقط**، لا
   يُعتمَد كنهائي (نفس "المبدأ" الأصلي أدناه: لا نفترض mapping غير آمن).
3. **Map** (`PATCH /imports/jobs/:id/mapping`): المستخدم يراجع/يعدّل
   الربط. يُرفَض حفظ ربط تنقصه حقول مطلوبة، أو يشير لفهرس عمود خارج
   النطاق.
4. **Preview** (`GET /imports/jobs/:id/preview`): يُعيد قراءة الملف
   وتحقيقه بالكامل في الذاكرة، **بلا أي كتابة لقاعدة البيانات — ولا حتى
   لصف المهمة نفسه**. يُرجع إجمالي/صالح/به أخطاء + عيّنة من الصفوف + عيّنة
   من الأخطاء.
5. **Validate** (`POST /imports/jobs/:id/validate`): نفس منطق التحقق،
   لكن يُخزَّن على المهمة (`validRows`/`errorRows`/`validationErrors`
   محدودة العدد) وتتحول الحالة لـ`validated`.
6. **Confirm** (`POST /imports/jobs/:id/confirm`): **الكتابة الفعلية
   الوحيدة**. يُعيد التحقق من الصفوف من جديد (دفاعيًا — الوقت قد يكون مرّ
   منذ Validate وتغيّرت بيانات قاعدة البيانات)، ثم يكتب كل صف صالح عبر
   الخدمة الموجودة أصلًا لنوعه (راجع القسم 5).
7. **Audit**: كل خطوة حسّاسة (`imports.job.upload`،
   `imports.job.mapping.set`، `imports.job.validate`،
   `imports.job.import.start`، `imports.job.import.complete`،
   `imports.job.cancel`) مسجَّلة عبر `AuditService` الموجود أصلًا — من
   قام بالعملية، متى، على أي منشأة، أي نوع استيراد، وعدد الصفوف/النتيجة.
   كل صف يُنشأ فعليًا يُدقَّق أيضًا بشكل مستقل عبر تدقيق الخدمة المستهدفة
   نفسها (`products.product.create`، إلخ) — بلا ازدواج.

## 5) لماذا لا منطق مخزون/كتالوج/أطراف موازٍ

كل صف صالح يُمرَّر مباشرة إلى نفس دالة الخدمة التي يستخدمها أي طلب API
عادي، فيمر بكل قيد موجود أصلًا (SKU فريد لكل منشأة، مرجع عميل/مورد فريد،
نطاق الفروع للمخزون، ...):

| نوع الاستيراد   | الخدمة المستدعاة |
|------------------|-------------------|
| `products`       | `ProductsService.create` |
| `barcodes`       | `ProductsService.addBarcode` |
| `categories`     | `CatalogService.createCategory` |
| `units`          | `CatalogService.createUnit` |
| `customers`      | `CustomersService.create` |
| `suppliers`      | `SuppliersService.create` |
| `opening_stock`  | `InventoryService.setOpeningBalance` |

مراجع الأسماء (تصنيف/علامة تجارية/وحدة لمنتج، تصنيف أب لتصنيف) تُتحقَّق
أنها **موجودة بالفعل لنفس المنشأة** قبل الاستيراد — **لا تُنشَأ تلقائيًا**
حتى لو لم تُوجَد، لتجنّب افتراض mapping غير آمن (صف به خطأ إملائي في اسم
تصنيف يجب أن يُرفَض، لا أن يُنشئ تصنيفًا جديدًا خطأً).

## 6) التحقق (Validation)

لكل صف: الحقول المطلوبة، أنواع البيانات (أرقام صحيحة الصيغة)، صيغة
الباركود، SKU/باركود/رقم مرجعي مكرر **داخل الملف نفسه** (بفحص Set أثناء
المرور على الصفوف) وأيضًا **مقابل البيانات الموجودة فعليًا** (استعلام
مجمَّع واحد `IN (...)` قبل حلقة الصفوف، لا استعلام لكل صف — لا N+1)،
ملكية مراجع التصنيف/العلامة/الوحدة لنفس المنشأة، وصحة الرصيد الافتتاحي
(الكمية ≥ صفر، المنتج موجود). رسائل الخطأ محدَّدة بالصف والحقل
(`"الصف 17: SKU مطلوب"`) لا رسالة عامة.

**ملف خاطئ لا يُفسِد الاستيراد بالكامل بشكل غير متوقَّع**: كل صف يُستورَد
داخل معاملة (`withTenant`) منفصلة عن بقية الصفوف — فشل صف واحد (تحقق
فاشل، أو خطأ سباق حقيقي مثل تكرار متزامن) يُسجَّل كخطأ لذلك الصف فقط
ولا يُوقف استيراد بقية الصفوف الصالحة. النتيجة النهائية (عدد المستورَد
فعليًا مقابل عدد الأخطاء) واضحة ومُدقَّقة دائمًا - هذا سلوك مُصمَّم
ومُبلَّغ عنه، وليس فسادًا صامتًا.

## 7) Idempotency وإعادة المحاولة

- **إنشاء المهمة**: `clientReferenceId` اختياري، نفس نمط
  `Sale`/`Purchase`/`Expense` بالضبط — فهرس فريد `(companyId,
  clientReferenceId)`، إعادة إرسال نفس الطلب تُرجع نفس المهمة الأصلية
  دون رفع ملف مضاعف.
- **Confirm**: مؤمَّن على مستوى المهمة نفسها أيضًا — استدعاء `confirm`
  على مهمة `completed` أو `importing` بالفعل يُرجع حالتها الحالية فورًا
  دون إعادة استيراد الصفوف (اختُبِر: استدعاء `confirm` مرتين لا يُنشئ
  المنتج مرتين).

## 8) الأداء والحدود (موثَّقة صراحة لهذه المرحلة)

`backend/src/modules/imports/constants/import-limits.ts`:

- **حجم الملف**: 5 ميجابايت كحد أقصى (`MAX_IMPORT_FILE_SIZE_BYTES`).
- **عدد الصفوف**: 5000 صف كحد أقصى (`MAX_IMPORT_ROWS`) — ملف يتجاوزه
  يُرفَض بالكامل (لا اقتطاع صامت).
- **أخطاء مخزَّنة**: أول 500 خطأ فقط (`MAX_STORED_VALIDATION_ERRORS`) على
  صف المهمة (للتدقيق)، لا كل خطأ من آلاف الصفوف.

الملف يُقرأ بالكامل في الذاكرة عبر `exceljs` (لا Streaming) — مقبول عند
هذه الحدود، وليس مناسبًا لملفات أكبر بكثير. لا Queue/معالجة خلفية في هذه
المرحلة (الملفات صغيرة بما يكفي لتُعالَج ضمن دورة الطلب/الاستجابة نفسها؛
كل استدعاء API قصير العمر) — نقطة توسّع واضحة لاحقًا إن احتاج حجم أكبر.

## 9) الأمان

- **نوع الملف**: بصمة ZIP الحقيقية (`PK\x03\x04`) تُتحقَّق قبل أي تحليل،
  بصرف النظر عن الامتداد أو Content-Type المُرسَل من العميل.
- **Formula/CSV injection**: أي قيمة نصية حرة مصدرها خلية مستوردة (اسم
  منتج/عميل/مورد/عنوان/ملاحظات) تُعالَج عبر `sanitizeImportedText` — قيمة
  تبدأ بـ`=`/`+`/`-`/`@` تُسبَق بعلامة اقتباس مفردة قبل أي تخزين، فلا
  تُنفَّذ كصيغة لو أُعيد تصديرها لاحقًا وفُتِحت في Excel/Sheets.
- **Path traversal**: مستحيل بنيويًا (مفاتيح تخزين مولَّدة من الخادم
  فقط، راجع القسم 1) + تحقق دفاعي إضافي في `LocalFileStorageProvider`.
- **وصول غير مخوَّل للملفات**: كل قراءة داخلية تمر عبر تحقق ملكية
  `companyId` + RLS. لا Endpoint لتنزيل ملف خام. لا مسارات نظام ملفات
  تظهر لأي مستخدم في أي استجابة API.
- **لا تسريب بيانات حسّاسة في الـLogs**: `LoggingInterceptor` (Milestone
  2) لا يسجّل جسم الطلب أصلًا — محتوى الملفات المرفوعة لا يصل لأي سجل
  Log إطلاقًا، لا في هذه الوحدة ولا في أي مكان آخر بالتطبيق.
- **RBAC**: صلاحيتان جديدتان فقط — `import.read` (عرض السجل)،
  `import.create` (رفع/تنفيذ استيراد) — Owner/Manager/Inventory Manager
  افتراضيًا، Accountant يملك `import.read` فقط (تدقيق دون تنفيذ)،
  Cashier لا يملك أيًا منهما. لا RBAC جديد اختُرِع — نفس نظام
  `RequirePermissions`/`PermissionsGuard` الموجود أصلًا.
- **RLS + IDOR**: `import_jobs` بنفس نمط `FORCE ROW LEVEL SECURITY` +
  `tenant_isolation` كأي جدول تجاري آخر. محاولة الوصول لمهمة استيراد
  تخص منشأة أخرى (Get/Mapping/Preview/Validate/Confirm/Cancel) تُرفَض
  بـ404 (مُختبَر e2e).
- **نطاق الفروع/المستودعات**: استيراد رصيد افتتاحي يمر عبر نفس فحص نطاق
  الفروع الذي يفرضه `InventoryService.setOpeningBalance` أصلًا — عضو
  مقيَّد بفرع لا يستطيع استيراد رصيد لمستودع خارج فرعه، حتى لو كان
  المستودع مملوكًا لنفس المنشأة (مُختبَر e2e).

## 10) الواجهة الأمامية

`frontend/src/pages/ImportPage.tsx` (`/import`) — صفحة واحدة تتبع
الحالة الحقيقية لـ`ImportJob` عبر كل الخطوات، بلا أي بيانات وهمية:
اختيار نوع البيانات → رفع الملف → مراجعة/تعديل الربط → معاينة → تحقق →
تأكيد → نتيجة، بالإضافة لسجل عمليات استيراد سابقة (`import.read`).
Loading/Error/Success state لكل خطوة، متوافقة مع RTL والتصميم المتجاوب
الموجودَين أصلًا (Milestone 2) — لا إعادة بناء لبنية الواجهة الأمامية.
